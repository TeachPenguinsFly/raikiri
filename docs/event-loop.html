Событийный цикл, C++ и Python

Почему await_response выглядит костылём, чем модель Boost.Asio отличается от asyncio — и в чём она на самом деле та же самая.

Написано по следам аварии 10 сентября 2026: шесть гейтвеев из восемнадцати умерли за пять минут из-за колбэка, писавшего в умерший кадр стека.

Короткий ответМы можем ровно как в Python. Asio это умеет.

Это не ограничение языка и не нехватка библиотеки. У Asio есть полноценные корутины C++20: asio::awaitable<T>, co_await, co_spawn. Код читается почти буква в букву как async def / await.

Причина, по которой raikiri этого не делает, — не «C++ так не может», а три конкретных решения в этом проекте. Каждое из них можно пересмотреть, но каждое было принято не случайно, и одно из них стоит нам дороже остальных вместе взятых.

1Одно и то же, двумя синтаксисами

Сначала уберём мистику. Вот одна и та же программа: загрузить каталог инструментов по HTTP и напечатать, сколько их.

Python · asyncio
# Корутина: приостанавливается на await,
# возвращая управление циклу.
async def load_catalogue(session):
    r = await session.get("/instruments")
    return await r.json()

async def main():
    async with ClientSession() as s:
        cat = await load_catalogue(s)
        print(len(cat))

asyncio.run(main())
# ^ создаёт цикл, крутит его,
#   пока main() не закончится
C++ · Boost.Asio
// Корутина: приостанавливается на co_await,
// возвращая управление io_context.
awaitable<Catalogue> load_catalogue(RestClient& rest) {
    auto r = co_await rest.async_send(req, use_awaitable);
    co_return parse(r);
}

awaitable<void> main_coro(RestClient& rest) {
    auto cat = co_await load_catalogue(rest);
    std::print("{}\n", cat.size());
}

io_context ioc;
co_spawn(ioc, main_coro(rest), detached);
ioc.run();   // ^ это и есть asyncio.run()

io_context — это event loop, ничем не более экзотический, чем питоновский. ioc.run() — это asyncio.run(): крутить, пока есть что делать. co_spawn — это asyncio.create_task().

Если модель та же, откуда взялось непонимание

Из того, что в raikiri главный цикл — не ioc.run(). Всё остальное — следствие. Ниже разберём, почему так вышло и чем за это плачено.

2Модель Asio: одна операция, много стилей

Главная идея Asio — completion token. У каждой асинхронной операции последним аргументом идёт «токен завершения», и он один определяет стиль. Операция одна, а как вы её получаете — ваш выбор на месте вызова. 

socket.async_read_some(buf, [](auto ec, auto n) { ... });  // колбэк
socket.async_read_some(buf, use_awaitable);                 // корутина: co_await
socket.async_read_some(buf, use_future);                    // std::future
socket.async_read_some(buf, deferred);                      // отложить и скомпоновать

В Python выбора нет: всё — корутины. В Asio выбор есть, и это одновременно его сила и источник путаницы — три разных примера из интернета могут делать одно и то же тремя несовместимыми на вид способами.

Где выполняются обработчики

Asio реализует Proactor: вы регистрируете операцию, ядро её выполняет, а обработчик завершения запускается на том потоке, который прямо сейчас находится внутри run() или poll() этого io_context. Отсюда всё остальное:

  • Один поток в run() — обработчики никогда не пересекаются, блокировки не нужны. Это модель Python, и это модель raikiri.
  • N потоков в run() — пул; обработчики идут параллельно, и связанные надо сериализовать через strand (аналог блокировки, но без блокировки).
  • io_context{1} — это подсказка, что поток будет один. Она включает оптимизации, но ничего не запрещает.

3Почему у нас не так

Гейтвей обслуживает не только сокеты. Он ещё вычитывает командные кольца в разделяемой памяти — на скорости спина, потому что отмена ордера не должна ждать сеть. Поэтому главный цикл принадлежит нам, а реактору достаётся срез.

Что делает raikiri
while (!stop) {
    drain_command_rings();   // shm, спин
    io.poll();               // один срез цикла
    publish_heartbeat();
    park_if_idle();          // 1 мс сна
}

poll() — законный режим Asio: выполнить готовые обработчики и вернуть управление, не блокируясь.

Как это выглядело бы в Python
while not stop:
    drain_command_rings()
    loop._run_once()       # так никто не делает
    publish_heartbeat()
    park_if_idle()

В Python это приватный метод, и лезть в него считается дурным тоном. В Asio то же самое — часть публичного интерфейса, потому что игровые движки и торговые системы иначе не умеют.

Отсюда обязан появиться мост

Каталог инструментов нужно загрузить до того, как цикл начнётся: гейтвей не имеет права подписываться, пока не знает размеры тика. А main() не корутина. Значит, кто-то обязан заблокироваться и крутить цикл, пока не придёт ответ.

Python даёт это из коробки
cat = loop.run_until_complete(
    asyncio.wait_for(load_catalogue(s), timeout=20)
)
Мы написали это руками
auto cat = await_response(io, clock, rest, req, 20'000);

await_response — это run_until_complete. Не костыль и не экзотика: ровно та же функция, которую Python даёт готовой, написанная руками, потому что Asio не поставляет её для режима «цикл кручу я сам».

4Три ловушки, и только одна из них про C++

Ловушка 1. use_future — то же самое, что вызвать run_until_complete внутри работающего цикла

asio::use_future выглядит как очевидный ответ на «хочу подождать». Но ждать future нужно с другого потока: тот, кто обязан крутить цикл, встанет в ожидание результата, который без него не появится.

В Python правило буквально то же. И вот настоящая разница между языками:

→ Python падает громко
RuntimeError: This event loop is already running
→ C++ молчит
// deadlock — или, в режиме poll(),
// тихая реентрантность: обработчики
// выполняются посреди чужой транзакции

Именно поэтому в IoContext появился флаг pumping(), а await_response теперь отказывается работать, если его позвали изнутри обработчика. Это попытка вернуть громкость, которая у Python есть даром.

Ловушка 2. Захват по ссылке — вот это уже чисто C++

Это та самая авария. В Python замыкание, захватившее локальную переменную, удерживает объект живым — на нём висит ссылка. В C++ захват по ссылке не удерживает ничего.

→ Python: так нельзя написать
def await_response(loop, coro):
    result = None
    def done(fut):
        # result жив, пока жива эта функция
        nonlocal result
        result = fut.result()
    ...
→ C++: так было написано
std::optional<RestResponse> result;   // на стеке
rest.send(req, [&result](RestResponse&& r) {
    result = std::move(r);            // ← в мёртвый кадр
});
// по таймауту выходим, НИЧЕГО не отменив.
// Колбэк остался жив внутри пула.
return result;

Когда зависал DNS, ответ приходил минутами позже — в стек, который занял уже следующий вызов. Одна запись в освобождённую память, и дальше падало что угодно: испорченные метаданные malloc, разваленный unordered_map в разборе стакана, повисшая категория error_code.

Починка — три строки: положить ответ в shared_ptr, которым владеет сам колбэк. Ровно то, что подсчёт ссылок в Python делает автоматически.

Ловушка 3. Корутины эту ловушку не убирают

Я сам так думал и ошибался. Мост block_on обязан блокироваться — и его собственный обработчик завершения захватывает его локали. Тот же дефект, этажом выше. Когда мы писали экспериментальный мост, он воспроизвёлся сразу, и пришлось делать ту же ячейку в куче.

Корутины меняют не то, блокируемся ли мы, а кто владеет кадром: кадр корутины живёт в куче и принадлежит handle. Это ценно — но ровно то же свойство мы уже получили пятнадцатью строками.

5Как это делают в проектах

Отдельный поток под реактор

Самый частый. «Моё приложение не асинхронное, но в нём есть сеть».
io_context ioc;
auto guard = make_work_guard(ioc);
std::thread io_thread([&]{ ioc.run(); });

// откуда угодно, кроме io_thread:
auto fut = async_op(..., use_future);
auto answer = fut.get();          // блокируемся безопасно

Здесь use_future работает — цикл крутит другой поток. Цена: общие данные становятся межпоточными, и появляются блокировки, которых у нас сейчас нет ни одной.

co_spawn + ioc.run() как вся программа

Форма Python. Новые кодовые базы на Asio, серверы, прокси.
int main() {
    io_context ioc;
    signal_set signals(ioc, SIGINT, SIGTERM);
    signals.async_wait([&](auto, auto){ ioc.stop(); });

    co_spawn(ioc, server(), detached);
    ioc.run();          // всё живёт внутри
}

Самая чистая. Требует, чтобы весь ввод-вывод был асинхронным: одна блокирующая функция посреди корутины останавливает весь цикл, как и в Python.

poll() внутри своего цикла

Игровые движки, симуляции, торговые системы. Наш случай.
while (running) {
    tick_simulation();
    ioc.poll();
    render();
}

Берут, когда у приложения уже есть собственный такт и отдавать его реактору нельзя. Расплата — мост, который мы обсуждали, и необходимость помнить, что вложенный poll() реентрантен.

Boost.Cobalt

Отдельная библиотека в Boost, специально чтобы корутины ощущались как в Python.
cobalt::main co_main(int, char*[]) {
    auto answer = co_await fetch();
    co_return 0;
}

Прячет io_context и co_spawn за единственным циклом на поток — буквально asyncio. Молодая, и предполагает, что цикл её.

6Что вышло, когда мы попробовали

Мы не рассуждали, а померили: перевели одну площадку на корутины в отдельном дереве и посчитали, во что это обходится сборке. База — 412 единиц трансляции, из них boost/asio сегодня видят восемь, потому что libs/net — фасад на pimpl, через который не проходит ни один сторонний тип.

Пресет rel, M4 Pro, -j3, три прогона на вариант. Инкрементальная — после правки net/rest_client.hpp.
Вариант Чистая Инкрем. TU с asio Вердикт
Сейчас: колбэк + poll 147.7 с 59.6 с 8 —
awaitable в виртуальных заголовках 153.8 с 63.9 с 123 нет
asio, спрятанный в .cpp +0.6 с/TU — +25…69 нет
Стёртый тип net::Task ≈ без изменений ≈ без изменений 9 можно

Секунды оказались не страшными: +2.7% на чистой сборке. Останавливает второе — asio расползается с восьми единиц трансляции на 123, то есть на 30% дерева, и Boost::headers становится публичной зависимостью raikiri::exec, от которой зависит всё. Это удаляет единственное свойство, ради которого libs/net вообще существует.

Вариант со стиранием типа границу держит — ноль новых единиц трансляции с boost, +2 аллокации на холодный вызов, 131 строка машинерии. Он написан и лежит в ветке. Но он не чинит аварию: её починил shared_ptr.

Где мы сейчас

await_response живёт в одном месте вместо семнадцати копий, ответ приземляется в ячейку кучи, которой владеет колбэк, очередь REST стареет по своему дедлайну, резолв ограничен таймером, а вложенный вызов изнутри обработчика отклоняется.

Три места, где он ещё вызывается, — все законные: загрузка каталога и синхронизация часов на старте, до цикла; и пуллы аккаунт-поллера, у которого свой поток и свой реактор. Единственное нарушение — переоткрытие сокета KuCoin, державшее главный цикл до десяти секунд, — убрано.

Так что вопрос «переходить ли на корутины» остался, но он больше не про безопасность. Он про читаемость и композицию, и решать его можно спокойно.
